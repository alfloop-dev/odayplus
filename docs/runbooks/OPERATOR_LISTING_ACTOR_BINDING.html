Operator Listing 的登入身分與重播綁定

工程候選，待獨立 source/task review；不是正式上線批准。依據 Assisted Listing authorization matrix 的角色、所有權與雙人覆核規則，以及跨契約的稽核／冪等要求。

必須消除的來源錯誤

舊 HTTP handler 接受 body.actorName or principal.subject_id，而 service 把該值用作 owner、submitter、audit actor 與 promotion proposer。受控重現中，登入 subject 101 填 actorName 102，實際提交者 fresh GET 得 403，102 卻得到 200。

八個寫入入口

入口新的身分來源
Listing convert／merge／archive登入 subject 與 verified platform role；client actorName／actorRoleId 不作授權或稽核事實。
Intake submit／correct／decide／retry／promote相同的登入身分綁定；提交／重試的 tenant 來自 verified scope，promotion proposer 不從舊 display name 猜測。

既有 action、parent resource 與五個範圍軸的授權仍在服務呼叫之前執行。第一提案者由持久化 source proposer／submitter 讀取；X-First-Actor-Id 不能取代它。Promotion domain actor 使用實際角色對應，不把所有人一律標成 staff。

seed_fixtures=false 的 service 在重播前要求非空 UUID actor／tenant 與 canonical platform role；租戶必須與 service 的實際 tenant binding 相同。缺少身分時不再填虛構姓名或預設 production tenant。fixture mode 的既有 synthetic identifiers 僅用於隔離測試，不能當作真實帳戶、UAT 或准入證據。

呼叫者與請求內容的重播邊界

收據以租戶 repository、實際 actor、action、key 綁定；request SHA-256 包含 resource ID、目標、欄位、原因與風險確認等實際命令內容。相同 actor／key 改變內容回 IDEMPOTENCY_CONFLICT，不重新執行；不同 actor 的 key 不共享收據。client display/persona 欄位不會改變 actor binding 或指紋。

新的 IntakeIdempotencyRecord 保存 actor_subject_id 與 request_sha256，重新建構 service 後仍檢查。沒有這些來源證據的舊收據回 UNBOUND_LEGACY_REPLAY，原資料保留，不從姓名推導 UUID、補造 proof 或再執行。歷史對帳與切換仍需批准。

重複 URL 的既有收件在保存新收據／回傳之前重新接受完整 resource scope 與 ownership 檢查；提交重播也讀取當前父收件來授權，不能用舊成功 envelope 的 scope 代替目前範圍。正式 service 缺少該授權 context 時回 INTAKE_SCOPE_CONTEXT_REQUIRED。重播入口的 HTTP guard 每次重新驗證登入、session 與角色，撤權不能靠 cache 取回舊成功。

重試與前端

Retry 接受 Idempotency-Key；正式模式與其他 governed writes 一樣要求 key/correlation context。typed client 與 intake transport 傳遞該 key，caller 可重用明確 key；未指定時 transport 產生新命令 key。舊 UI 的四個提交流程不再把角色 label 當人名送出。這沒有建立新的業務政策或授予角色。

驗證範圍與仍待完成項目

測試包括真實簽章 token 驗證、server principal map、local account/session/current roles、偽造 claims/headers/body、不同 actor 同 key、內容衝突、私有 duplicate、各入口 attribution、UUID production checks、durable restart 與不可自動歸屬的 legacy receipt。所有 identity、records、policies 均為明示隔離 synthetic inputs。

完整系統仍需 Operator/v1 canonical Intake UUID 與 Workflow physical owner 整合、真正 correction/review/job audit 與 outbox/WORM delivery、account display lookup、歷史對帳、完整 UI 稿比對、六角色實際 UAT、正式資料／政策／模型、獨立審查與當前 Gate 0–6 GO。既有 Operator envelope、IN 顯示 ID 或 audit presentation ID 不能當作 physical canonical 關聯已完成。不得以本文件或局部測試宣告正式驗收。
